# [SKELT-2] Minutes

<!-- Categories: Pivot | Insight | Decision | Finding | Lesson | Milestone | Open | Resolved -->

- 2026-05-20 **Finding**: The published v0.1.0 tarball on npm contains the raw `src/` tree (24 files) with no `dist/`, no `main`, no `exports`. A consumer who runs `npm install @guise/skeleton` receives only unminified, non-version-stamped source files; bare specifier resolution fails entirely.
- 2026-05-20 **Decision**: Scope this ticket to publishing metadata only (`package.json` fields, `prepublishOnly` gate, `readme.md` consumer documentation). Build-pipeline modernization remains deferred from [SKELT-1]. Guise Mummy npm-asset integration is a separate concern.
- 2026-05-29 **Decision**: License file uses `license.md` (lowercase, consistent with project's `readme.md` convention). GitHub's licensee gem recognizes `license.md` via its filename regex. Contains the full Apache 2.0 license text in Markdown format.
- 2026-05-29 **Decision**: Exclude `src/` from the published tarball. The build adds only a `@charset` header and version stamp — the unminified `dist/` files *are* effectively the sources. Shipping both would be near-duplicate content.
- 2026-05-29 **Decision**: Version-management scripts (`release:prepare`, `develop:prepare`) use `npm pkg set` for `package.json` writes rather than `JSON.parse`/`JSON.stringify` whole-file rewrite. `npm pkg set` is npm's semantic field-update API; it preserves formatting and touches only the specified field.
- 2026-05-29 **Decision**: `prepublishOnly` includes an inline SNAPSHOT guard (`node -e "…"`) that refuses to publish if the version still contains `SNAPSHOT`. Defense-in-depth against the most common publish mistake.
- 2026-05-29 **Insight**: npm has no shared local repository analogous to Maven's `~/.m2/repository`. For cross-project snapshot iteration, `link:../sibling` in `package.json` (creates an NTFS junction on Windows) is the standard mechanism; `npm pkg set` / `npm pack` + install is the dress-rehearsal path.
- 2026-05-29 **Finding**: `npm pkg set` (available since npm v8) is the semantic, official API for modifying individual `package.json` fields. It auto-detects indentation, preserves key ordering, and writes back with a trailing newline — eliminating the need for manual `JSON.stringify` serialization in scripts that modify `package.json`.
- 2026-05-29 **Milestone**: Plan implemented (Steps 1–6). `package.json` declares `files`, `main`, `style`, `sideEffects`, `exports`, `prepublishOnly`, `release:prepare`, and `develop:prepare`. `license.md` has copyright line. `readme.md` documents bundler, direct-reference, and CDN consumer paths plus publishing workflow. `npm pack --dry-run` confirms tarball contains only `dist/css/*`, `license.md`, `readme.md`, and `package.json`.
- 2026-05-29 **Finding**: Published source maps (`dist/css/*.min.css.map`) reference `src/` paths via `sources` without embedding `sourcesContent`. Since `src/` is excluded from the tarball, browser devtools cannot reconstruct original source from the npm-installed package. The unminified `dist/css/*.css` files serve that role instead. Fixing requires build pipeline changes (out of scope).
- 2026-05-29 **Decision**: Defer SemVer validation in `develop-prepare.mjs`. The script currently rejects only `-` (prerelease suffixes). Full validation (build metadata, non-version strings) would require the `semver` package or a complex regex. `npm publish` is the eventual gatekeeper; bad input is caught there.
- 2026-05-29 **Pivot**: Removed per-project version-management scripts (`scripts/release-prepare.mjs`, `scripts/develop-prepare.mjs`, and their `package.json` entries). Version management belongs in general-purpose workflow scripts (`npm-prepare-release.sh`, `npm-prepare-develop.sh`, `npm-get-ver.sh`) stored in a shared tools repository, parallel to the existing Maven workflow scripts. Those scripts use `npm version --no-git-tag-version` (which validates SemVer) rather than `npm pkg set` (which does not).
- 2026-05-29 **Lesson**: `npm version <ver> --no-git-tag-version` validates SemVer and writes the version field — strictly better than `npm pkg set version=<ver>` for version updates, because it gives free input validation. The existing `npm-set-ver.sh` already used this approach; the per-project scripts should have followed suit rather than reinventing with `npm pkg set`. Check existing tooling before creating new scripts.
